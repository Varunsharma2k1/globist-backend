TripTape system architecture

High-level design for a travel app where short reels drive trip bookings. It can run for about $23 a month for the first 1k users and grows to a million monthly users by adding capacity, not by rewriting. Click a flow to follow one request through the system.

HLD v1 · Nov 2026
AWS ap-south-1 (Mumbai) + Cloudflare
Node.js · PostgreSQL · Redis · R2

The three request flows

The numbers match the badges in the diagram.

A · Watch the reel feed

GET /api/feed · p95 target < 150 ms

  1. 1App → Cloudflare → ALB → gateway. The JWT is checked and one rate-limit token is taken from Redis.
  2. 2Feed service reads the precomputed feed from Redis (feed:{userId} sorted set). Around 95% of reads end here, in about 5 ms.
  3. 3On a miss it rebuilds from a Postgres read replica (followed creators + trending in the user's region) and writes the result back with a 10-minute TTL.
  4. 4The response carries reel metadata. The player streams HLS from the Cloudflare CDN and picks 240p–720p to suit the connection.
  5. 5On a CDN miss the segment is pulled from R2 once. Segments never change, so they're cached for a year.
  6. 6The app batches views and likes every ~10 s. Engagement does INCR in Redis, and the counter-flush worker writes totals to Postgres each minute.

B · Upload a reel

POST /api/reels/upload-url · async processing

  1. 1The app asks for an upload slot.
  2. 2Reels service writes the reel row as PROCESSING and returns a presigned R2 PUT URL that expires in 15 min.
  3. 3The app uploads the raw video straight to R2, so the API servers stay small and cheap.
  4. 4R2 emits an ObjectCreated event (Cloudflare Queues → bus). If it's missed, the app's "upload complete" call acts as a backup.
  5. 5A transcode worker on Fargate Spot picks up the job.
  6. 6FFmpeg writes HLS renditions (240/480/720p) and a thumbnail to the public media/ bucket.
  7. 7Workers mark the reel READY, index it for search and push its ID into followers' feeds. Most creators use fan-out on write; creators with 10k+ followers use fan-out on read.

C · Book and pay for a trip

POST /api/bookings · saga over Razorpay

  1. 1The app sends POST /bookings with an Idempotency-Key header, so a retry can't create a second booking.
  2. 2Booking holds the seat: SET hold:{trip}:{date} NX EX 600. A second buyer is told it's held straight away.
  3. 3In one Postgres transaction: booking PENDING + UPDATE slots SET left = left − n WHERE left >= n. If no row updates, the trip is sold out, so nothing can be sold twice.
  4. 4Payments creates a Razorpay order using the server-side price. The app then opens Razorpay Checkout (UPI / card / netbanking).
  5. 5When Razorpay's webhook arrives, Payments checks its HMAC signature and ignores repeats of the same payment_id.
  6. 6A single transaction sets the booking to CONFIRMED, adds a ledger entry and writes a BookingConfirmed row to the outbox.
  7. 7The outbox relay publishes the event to the bus. If the app crashes, no event is lost.
  8. 8The reconciler schedules the agency payout through Razorpay Route. If payment fails or the hold expires, it refunds and releases the seat (saga compensation).
  9. 9The notifier sends a push (FCM/APNs) plus an SMS and email confirmation.

Where caching happens

Four layers. Each request should stop at the first one that has the answer.

L1 · DEVICE

App cache

React Query caches API responses. The player prefetches the next 2 reels' first segments, so swipes start instantly.

TTL: session · cost $0
L2 · EDGE

Cloudflare CDN

HLS segments, thumbnails, images. Content-hashed URLs with Cache-Control: immutable. Public explore/trip pages cached for 60 s.

target hit ratio ≥ 95%
L3 · APP

Redis

Cache-aside for feeds, reel cards, trip details and counters. Delete the key when the data is written; add TTL jitter so many keys don't expire at once.

target hit ratio ≥ 90%
L4 · DATABASE

Replicas + buffer pool

Read replicas take feed rebuilds and explore queries. Size the instance so the working set fits in RAM.

primary: writes + money only

Why R2 + FFmpeg over Mux or Stream

Managed video services bill per minute watched. At 200M views × ~30 s that's ~100M minutes, about $100k/mo at $1 per 1,000 minutes. R2 + CDN delivery costs about $430. Managed transcoding (MediaConvert) would be ~$5k/mo against ~$200 for Spot FFmpeg.

Biggest line to watch: SMS OTP

At scale, OTP SMS costs more than Redis. Offer WhatsApp OTP, Google/Apple sign-in or email magic links first, use SMS as the fallback, and rate-limit OTP requests per number.

Start as one deployable

Keep the nine services as modules in one Node.js app with clear boundaries. Split out Media and Payments only when they need to scale or deploy separately. That saves a service mesh and a platform engineer.

System design concepts in use

Where each one appears in this design.

Traffic & scale

CDN + edge caching
Video and images served from Cloudflare points of presence in India.
Rate limiting (token bucket)
At the edge per IP, and in Redis per user/route. Stricter on OTP and booking.
Load balancing + horizontal autoscaling
ALB across 2 AZs. ECS scales on CPU and request count.
Stateless services
Sessions are JWTs plus a Redis refresh-token store, so any task can serve any request.

Data

Cache-aside with TTL jitter
Read Redis, fall back to the DB, write back. Delete the key on update.
Read replicas + connection pooling
PgBouncer stops autoscaled tasks running out of DB connections.
CQRS
Search and analytics are read copies built from events, apart from the main database.
Partitioning → sharding
Partition bookings and events by month first. Shard by user_id only after 1M+ MAU.
Hybrid feed fan-out
Fan-out on write for most creators, fan-out on read for very large ones.

Reliability & money

Idempotency keys
On booking creation and webhook handling, so retries never charge twice.
Distributed lock with TTL
Redis seat hold that expires on its own after 10 minutes.
Transactional outbox + saga
Events commit in the same transaction as the booking. Failed payments trigger compensating steps.
Retries, backoff, DLQ, circuit breaker
Around Razorpay, SMS and FCM calls, so a slow provider can't take the API down.
Multi-AZ + point-in-time recovery
RDS failover in under 2 min. 7–35 days of PITR backups.

Media

Presigned direct uploads
Clients upload straight to R2, so API servers never buffer 200 MB files.
Adaptive bitrate (HLS)
Three renditions, so a reel plays on 4G in Spiti as well as on Wi-Fi.
Spot workers
Transcode jobs can be retried, so cheap preemptible capacity is safe.

Security

Short-lived JWT + refresh rotation
15-min access tokens. Refresh tokens are revocable in Redis.
Card data stays with Razorpay
Card data never touches your servers, so the PCI DSS burden stays with Razorpay.
Webhook HMAC + least-privilege IAM
Signed callbacks only. Each service gets only the permissions it needs.

Operations

Observability (logs, metrics, traces)
OpenTelemetry trace IDs from the gateway to the worker.
Blue/green deploys + feature flags
Ship safely and roll back in one click.
Infrastructure as code
Terraform, so staging and production stay identical.

From today's codebase to this design

The current backend is Express + MongoDB on Vercel, with reels saved to a local uploads/ folder by multer. In order:

  1. Move reel uploads to R2 with presigned URLsVercel's filesystem is temporary, so files in uploads/reels are lost on redeploy. This is the most urgent fix.
  2. Add a transcode worker and serve HLS through the CDNReplace raw MP4 playback, which cuts startup time and data use on mobile.
  3. Move the API from Vercel functions to ECS FargateLong-lived processes keep DB pools warm and can run BullMQ workers. The Express code moves as-is.
  4. Put bookings and payments in PostgreSQL firstThen move users, reels and trips over in stages. MongoDB transactions can work as a stopgap, but row locks, constraints and the ledger fit Postgres better.
  5. Add Redis for feeds, holds and rate limits, then Razorpay webhooks + outboxAfter this, the booking flow can't double-sell and the feed reads from cache.

How DAU capacity was worked out

Each daily user is assumed to watch ~30 reels and make ~120 API calls a day, with 15% of a day's traffic in the busiest hour. That gives peak req/s ≈ DAU × 0.005. Video bytes come from the CDN, so they don't count against the servers.

The trade-offs at Tier 1

One server means a few minutes of downtime on deploys or failure, and no automatic failover. That's fine for a beta with under 1k users. Keep Neon's point-in-time restore and daily EBS snapshots switched on.

Not included

Razorpay's ~2% per transaction (deducted from payments), Apple's $99/yr and Google Play's $25 one-time developer fees, and your team's time. Free tiers and prices change, so treat these as ±25% and check before committing.
